Persistencia, respaldo y recuperación de sesiones

Los perfiles LocalAuth son credenciales. No los publiques, no los guardes en Git ni conectes simultáneamente una copia y el original. Una vinculación revocada por WhatsApp o por el usuario requiere un nuevo QR; un respaldo no puede reactivarla.

Comportamiento del servicio

  • Docker monta el volumen persistente en /app/sessions. storage-entrypoint.sh mantiene un flock exclusivo en .service.lock. Otro contenedor que use el mismo volumen debe esperar a que el anterior termine; nunca borres ese archivo para forzar acceso.
  • Eliminar/detener una sesión mediante DELETE escribe y sincroniza .disabled-ID antes de confirmar la baja. Conserva el perfil, impide la restauración automática y es idempotente aunque el navegador ya no exista.
  • Un inicio manual explícito quita esa marca y permite recuperar el mismo perfil. Para vincular un número distinto usa otro ID; no reutilices credenciales antiguas suponiendo que corresponden al nuevo teléfono.
  • La restauración, inicio manual, recuperación y eliminación comparten el bloqueo por ID. Los cierres deben confirmar la salida del proceso antes de retirar los SingletonLock. Si no puede confirmarse, el perfil queda bloqueado y se informa del error.
  • Al apagar se rechaza trabajo nuevo, se espera la actividad en curso y se coordinan los cierres con los arranques pendientes. Un cierre incompleto se registra y sale con error; no se presenta como un guardado correcto.

Proxies sin reinicios innecesarios

Guardar y aplicar son estados distintos. PUT settings persiste por defecto sin reiniciar. Solo restart: true solicita aplicar una configuración diferente al navegador; si el proxy efectivo y el modo ya coinciden, no reinicia. Las respuestas incluyen stored, applied y pending_restart. La sincronización de arranque y la actualización del pool guardan cambios pendientes sin cortar una conexión activa.

Una sesión con proxy propio deja una marca .proxy-required-ID, incluida en los respaldos. Si falta su configuración, no arranca por conexión directa ni por un proxy global. Un JSON corrupto también bloquea nuevos arranques hasta reparar la configuración. Estas protecciones se establecen al guardar con el código nuevo; no se modificaron las configuraciones de producción durante el desarrollo.

El backend confirma almacenamiento antes de cambiar la asignación en Mongo y conserva un estado desconocido si pierde la respuesta. Un candado temporal por instancia impide cambios simultáneos por las rutas de asignación y sincronización. Una confirmación de almacenamiento no se presenta como comprobación de salida real. Para esta última existe la consulta de IP del navegador, que utiliza el proxy con el que arrancó.

La salud de salida usa IPinfo y, si falla, el endpoint JSON documentado de ipify, siempre por el proxy. La respuesta alternativa no inventa país o ciudad para una IP nueva. Se conserva historial acotado de cambios de IP, sin cambiar de proxy por ese motivo. Solo se admiten proxies HTTP: HTTPS y SOCKS se rechazan explícitamente porque el relay actual no los implementa.

Un fallo de la comprobación externa no autoriza a cortar una sesión conectada o de estado desconocido. La sustitución automática, cuando está habilitada, se limita a una sesión por ronda tras fallos persistentes y con estado desconectado/error. Espera confirmación de reconexión y queda en pausa para revisión si no vuelve. Una reasignación manual explícita a un proxy diferente puede necesitar reiniciar Chromium; guardar con restart=false la deja pendiente para el siguiente arranque.

Preparación del respaldo

La supervisión distingue CONNECTED de estados que requieren QR o intervención. Se limitan las recuperaciones automáticas a tres por sesión en 15 minutos para frenar ciclos; al agotarse el presupuesto se informa de error y se debe revisar la causa antes de un inicio manual. La espera de un turno de recuperación no retiene el candado que necesita el apagado.

La herramienta usa Node sin dependencias adicionales: formato versionado, compresión gzip y cifrado autenticado AES-256-GCM con una clave aleatoria de 32 bytes. Incluye perfiles, configuración de sesiones y marcas de baja. Excluye los bloqueos temporales de Chromium y el bloqueo del servicio. La restauración verifica la autenticidad antes de extraer y solo publica en una carpeta nueva.

Crea la clave fuera del volumen y del repositorio. Guárdala aparte de los respaldos, en un gestor de secretos o almacenamiento seguro:

node sessionBackup.js init-key /ruta-segura/sesiones.wa-session-key

En Linux, después de detener el servicio de forma controlada, ejecuta desde el host o un contenedor de mantenimiento con acceso al mismo volumen y a la clave:

node sessionBackup.js backup /ruta/al/volumen/sessions /ruta/respaldos/2026-10-19.wa-session-backup /ruta-segura/sesiones.wa-session-key

El comando rechaza el respaldo si el servicio conserva el flock. No copies perfiles vivos de Chromium como sustituto de un respaldo consistente. Un servicio antiguo que todavía no use este entrypoint debe detenerse y verificarse antes de ejecutar la herramienta. Después puedes iniciar el servicio normalmente.

La herramienta genera el archivo local. No lo envía a ningún proveedor. Aún falta elegir el destino externo. Cuando exista, configurar transferencia cifrada con verificación de integridad, retención y alertas; mantener al menos una copia fuera del servidor. Hasta comprobar esa transferencia y recuperación, el respaldo externo no se considera implementado.

Comprobación de recuperación aislada

node sessionBackup.js restore /ruta/respaldos/2026-10-19.wa-session-backup /ruta/nueva/recuperacion-aislada /ruta-segura/sesiones.wa-session-key

La carpeta de destino no debe existir. Este comando no inicia Chromium ni conecta WhatsApp. Compara archivos y marcas de baja con el respaldo esperado. Antes de probar una reconexión real, detener y confirmar el cierre del original, montar el perfil en un único servicio y verificar el número y estado. Nunca abrir una segunda copia mientras el original siga activo.

Los archivos de prueba usados por las pruebas automatizadas contienen únicamente datos ficticios. No se ha hecho todavía una prueba real de reconexión ni una restauración de credenciales de producción.
